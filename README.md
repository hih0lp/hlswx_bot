# HWLS Pay Bot

Telegram-бот **@HwlsPaySystemBot** — подписки с ML-тарификацией, пакетные размещения, баланс, оплата ЮKassa.

Отдельный проект: **не связан** с hammer-bot и posting в коде. Публикует в те же Telegram-чаты (ID прописаны в `app/core/seed.py`).

---

## Стек

- Python 3.12, aiogram 3, FastAPI
- PostgreSQL 16, Redis 7
- Docker Compose
- ML: TF-IDF + LogisticRegression, pymorphy3
- Оплата: ЮKassa (YooKassa)

---

## Возможности

| Функция | Описание |
|---------|----------|
| **Подписка** | Текст → ML определяет тариф → город → чаты → оплата → публикация 30 дней |
| **Пакет** | Разово во все чаты города (MSK, SPB, NN, SMR) |
| **Баланс** | Пополнение от 100 ₽, оплата подписки/пакета с баланса |
| **Публикация** | По активной подписке, очередь по группам с тремя приоритетами |
| **Фрод** | Hash + similarity текста при публикации |
| **Whitelist** | Бесплатная подписка для выбранных пользователей |
| **Админка** | `/admin` — статистика, ML, whitelist, очередь, оплаты |

## Быстрый старт (локально / сервер)

### 1. Требования

- Docker и Docker Compose
- Токен бота от [@BotFather](https://t.me/BotFather)
- Ключи ЮKassa (shop_id + secret_key)

### 2. Настройка

```bash
cp .env.example .env
```

Заполните `.env`:

```env
BOT_TOKEN=ваш_токен_бота
ADMIN_IDS=ваш_telegram_id
OWNER_IDS=ваш_telegram_id

POSTGRES_PASSWORD=надёжный_пароль

YOOKASSA_SHOP_ID=...
YOOKASSA_SECRET_KEY=...

PUBLIC_URL=http://ВАШ_IP:8082
YOOKASSA_RETURN_URL=http://ВАШ_IP:8082/success
```

### 3. Запуск

```bash
docker compose up -d --build
```

Проверка:

```bash
curl http://localhost:8082/health
```

Должен вернуть `"status":"ok"`.

### 4. Telegram API (если сервер в РФ)

В `docker-compose.yml` уже есть:

```yaml
extra_hosts:
  - "api.telegram.org:149.154.167.220"
```

На хосте может понадобиться запись в `/etc/hosts`:

```
149.154.167.220 api.telegram.org
```

## ML — классификация и обучение

Бот определяет **тариф подписки** по тексту объявления. Это не ChatGPT, а классический ML на ваших примерах.

### Как это работает для пользователя

1. Клиент присылает текст объявления.
2. Бот определяет категорию (шабашка, вакансия, аренда и т.д.) и цену за 1 чат.
3. Если текста мало — просит дописать.
4. Если запрещённый контент — отклоняет по правилам (без ML).
5. Если ML не уверен (< 85%) — пробует ключевые слова; иначе тариф «Прочее» (3500 ₽).

Пользователю **не показывается** процент уверенности модели.

### Алгоритм

| Компонент | Что делает |
|-----------|------------|
| **Препроцессинг** | lowercase, лемматизация (pymorphy3), удаление ссылок, @username, телефонов |
| **Векторизация** | TF-IDF, n-граммы 1–2, до 15 000 признаков |
| **Классификатор** | LogisticRegression, `class_weight=balanced` |
| **Порог** | `ML_CONFIDENCE_THRESHOLD=0.85` в `.env` |
| **Подсказки** | При низкой уверенности — ключевые слова из `app/ml/preprocess.py` |

Файлы модели (создаются при обучении):

```
models/tariff_classifier.joblib   — сама модель
models/tariff_classifier.json     — метрики (accuracy, дата, число примеров)
```

В Docker модель хранится в **volume** `hwls_models` — не пропадает при пересборке контейнера.

### Когда модель обучается

| Событие | Что происходит |
|---------|----------------|
| **Первый запуск** | Если есть `data/training_dataset.xlsx`, но нет `.joblib` — обучение автоматически (`app/core/seed.py`) |
| **Перезапуск бота** | Модель **не** переобучается сама — загружается готовая из `models/` |
| **Кнопка в админке** | `/admin` → 🧠 ML → **Переобучить модель** |
| **После деплоя** | Если volume пустой — снова первичное обучение из Excel |

Проверить состояние ML:

```bash
curl http://IP:8082/health
```

В ответе: `ml_ready`, `ml_meta` (accuracy, samples, trained_at).

### Откуда берутся обучающие данные

При переобучении объединяются **два источника**:

1. **Excel** — `data/training_dataset.xlsx` (~296 примеров, базовый датасет)
2. **База PostgreSQL** — таблица `training_dataset` (`TrainingSample`), примеры из админки

Дубликаты по тексту: **последняя версия побеждает** (пример из БД перезаписывает Excel).

### Формат датасета Excel

Файл: `data/training_dataset.xlsx`, первый лист.

| Колонка | Содержимое |
|---------|------------|
| **A** | Полный текст объявления |
| **B** | (опционально) подсказки, в обучении не обязательна |
| **C** | Цена тарифа: `500`, `750`, `1200`… или слово **«отказ»** → категория REJECT |

Строки с «ЕЖЕДНЕВНЫЕ» в начале текста пропускаются.

**Соответствие цены и категории:**

| Цена | Категория |
|------|-----------|
| 500 | SHABASHKA — шабашка |
| 750 | BUY_SELL — куплю/продам |
| 1000 | RENT — аренда |
| 1200 | VACANCY — вакансия |
| 1500 | REFERRAL — рефералка |
| 1800 | GOLD — золото |
| 2500 | IP_OOO — ИП/ООО |
| 3000 | VERIFICATION — верификация |
| 3500 | ONLINE_WORK — работа онлайн |
| отказ | REJECT — запрещённый контент |

### Дообучение через админку

`/admin` → **🧠 ML**

| Действие | Описание |
|----------|----------|
| **➕ Добавить пример** | Один текст + выбор категории → сохраняется в БД |
| **📎 Загрузить файл** | Пачка примеров (.xlsx / .csv / .txt) |
| **📚 База примеров** | Последние добавленные записи |
| **📋 Логи классификаций** | Исправить ошибку бота (кнопки категорий / «Верно») |
| **🧠 Переобучить модель** | Excel + все примеры из БД → новая модель |

**Важно:** новые примеры попадают в работу бота **только после «Переобучить»**.  
Само добавление примера модель не меняет.

### Формат файла для загрузки

**Excel (.xlsx)** — как основной датасет (колонка A + C).

**CSV / TXT** — одна строка = один пример:

```
VACANCY|Ищу электрика на объект, оплата ежедневно...
1200|Ищу электрика на объект...
REJECT|текст с запрещённым содержанием
```

Разделитель: `|`, `;` или табуляция.

### Исправление ошибок в логах

Когда пользователь оформляет подписку, бот пишет классификацию в лог. Админ видит в **📋 Логи**:

- **✅ Верно** — пример сохраняется в БД как подтверждённый
- **🏷 Категория** — исправление: «должно быть VACANCY, а не SHABASHKA»

После накопления правок — **Переобучить**.

### Типичный цикл улучшения ML

```
1. Бот ошибся с тарифом
2. Админ → ML → Логи → исправить категорию
3. (Опционально) добавить ещё примеры текстом или файлом
4. ML → Переобучить модель
5. curl /health — проверить accuracy и samples
6. Протестировать на том же тексте
```

### Текущая точность

На базовом датасете (~296 примеров): **~73% accuracy**.  
Чем больше реальных примеров из логов — тем лучше на ваших текстах.

### Настройки ML в `.env`

```env
ML_CONFIDENCE_THRESHOLD=0.85
ML_MODEL_PATH=models/tariff_classifier.joblib
TRAINING_DATA_PATH=data/training_dataset.xlsx
```

### Замена базового Excel

1. Положить новый файл в `data/training_dataset.xlsx`
2. Пересобрать/перезапустить контейнер **или** переобучить из админки
3. При переобучении новый Excel объединится с примерами из БД

### Если модель не загрузилась

- В `/health` будет `ml_ready: false`
- Бот ставит тариф **OTHER (3500 ₽)** с пометкой на проверку
- Смотреть логи: `docker logs hwls_app`
- Частая причина: нет файла Excel при первом запуске или ошибка обучения

## Очередь публикаций и приоритеты

Очередь строится **по группам, а не по пользователям**. Пост, адресованный нескольким
группам, разбивается на независимые задачи — по одной на группу (`publish_jobs`),
объединённые одной публикацией (`publications`). Каждая группа хранит собственное
состояние в `chat_publish_locks` и разбирает свою очередь, не дожидаясь остальных.

### Три приоритета

| Приоритет | Кто | Поведение |
|-----------|-----|-----------|
| 1 — разовый пост | покупка в Hammer/W, пакет в этом боте | Публикуется немедленно и вне очереди, даже если группа в тишине. После выхода тишина ставится заново на 20 минут от времени этого поста |
| 2 — подписчик | ежемесячная подписка | Общая очередь на группу по времени постановки. Обгоняет белый список на освободившемся слоте |
| 3 — белый список | `WHITELIST`-подписка | Публикуется, если группа свободна и нет ожидающих постов подписчиков |

### Тишина и пауза

- **Тишина 20 минут** — по каждой группе отдельно, после разового поста. Посты
  подписчиков и белого списка в это время не отклоняются, а ждут своей очереди.
- **Пауза 2 минуты** — по каждой группе отдельно и только **между постами разных
  пользователей**. Пост одного пользователя уходит во все его группы одновременно,
  без внутренней задержки.

Настройки: `QUEUE_SILENCE_MINUTES` (20), `QUEUE_USER_PAUSE_SEC` (120),
`QUEUE_JOB_TTL_MINUTES` (120 — через сколько зависшая задача отменяется).

### Каналы публикации

Основной канал — релей в Hammer/W (`HAMMER_RELAY_URL`). Если релей выключен или
недоступен, при `DIRECT_PUBLISH_FALLBACK=true` бот публикует сам. Способ доставки
пишется в `publish_jobs.delivery`: посты, отправленные напрямую, бот может
редактировать и закрывать сам; для ушедших релеем нужны ручки на стороне Hammer.

### Уведомления и действия над постом

Пользователь получает одно уведомление на публикацию, которое обновляется по мере
разбора очереди: «опубликован» / «в очереди» / «опубликован частично» с перечислением
групп. Под опубликованным постом — кнопки «Редактировать» и «Закрыть».

Формулировки — временные заглушки, помеченные `TODO` в `app/core/texts.py` и
`app/services/publication_status.py`: финальные тексты берутся из макета Figma.

### Интеграция с Hammer / W

Чтобы разовый пост включал тишину, Hammer/W должны вызывать
`POST /api/hwls/oneshot-published` — контракт в **[docs/integration_hammer.md](docs/integration_hammer.md)**.
Пока этого нет, тишину можно ставить вручную:

```
/silence <chat_id|@username> [минут]
```

Состояния групп и зависшие задачи видны в админке: `/admin` → **Очередь**.

### Журнал

Все решения очереди пишутся в таблицу `publish_events` (публикация, ретрай, отказ,
установка тишины, пауза, правка, закрытие) и в лог приложения.

## Тесты

Тестовый контур поднимается отдельно и не трогает боевую БД и чаты:

```bash
docker compose -f docker-compose.test.yml run --rm tests
```

Покрыты все 10 сценариев из таблицы 6.5 ТЗ, идемпотентность вебхука разовых постов,
частичная публикация, редактирование и закрытие поста, переживание перезапуска.

### Две переменные, без которых треть тестов «падает»

Если гоняете тесты не через `docker-compose.test.yml`, а в окружении боевого
или тестового стенда, задайте их явно:

```bash
-e HAMMER_RELAY_ENABLED=false -e DIRECT_PUBLISH_FALLBACK=true
```

Иначе публикация в тестах уходит в **настоящий** релей Hammer и получает
`chat_not_found` — чаты в тестах выдуманные. Отключить один релей мало:
`relay_disabled` считается сбоем инфраструктуры и включает запасную публикацию
своим ботом, а её запрещает `DIRECT_PUBLISH_FALLBACK=false`. Нужны обе.
Симптом узнаётся сразу: 31 падение в шести файлах — публикации, очередь,
настройки, — при том что остальные проходят. С правильными переменными весь
набор зелёный (18.09.2026: 361 пройден, 3 пропущено).

Пропускаются только проверки соответствия макету (`tests/test_figma_parity.py`):
им нужен дамп `docs/design/figma.json`, а он в `.gitignore` — выгружается
скриптом `scripts/figma_fetch_images.py`.

## Резервные копии

Сервис `backup` в `docker-compose.yml` снимает дамп раз в сутки в том `hwls_backups`
с ротацией 14 дней. Проверка восстановления:

```bash
docker compose exec backup sh /scripts/restore_check.sh
```

Скрипт разворачивает последний дамп во временную БД и проверяет, что ключевые
таблицы читаются.
